# Third-party vendoring

Status: decided (2026-09). Supersedes nothing.

## Principle

Aegir commits **no** third-party source (project rule, `AGENTS.md`). Every
external component is:

1. pinned to an exact revision — a git SHA for a `repo` project, or a release
   tarball's sha256 together with its detached signature for a source with no
   reliable git remote,
2. fetched into a gitignored path on demand,
3. patched, if we need changes, from a tracked patch in
   `third_party/patches/`, and
4. verified against its pin by `make deps-check`.

## Mechanism: Google's `repo` tool

seL4 is not one repository but a coordinated set, and its build system hard-codes
the assumption that those repositories sit at specific paths relative to the
project root. Verified in the pinned sources:

- `cmake-tool/base.cmake` — `find_file(KERNEL_PATH kernel PATHS ${CMAKE_SOURCE_DIR})` and
  `find_package(musllibc REQUIRED)`; the ELF loader is located as
  `cmake-tool/../elfloader-tool`.
- `cmake-tool/projects.cmake` — globs `projects/*/CMakeLists.txt`.
- `cmake-tool/init-build.sh` — configures with `-DCMAKE_TOOLCHAIN_FILE=$SCRIPT_PATH/kernel/gcc.cmake`.
- `sel4test/settings.cmake` — derives `project_dir = <it>/../..` and expects
  `kernel/`, `tools/seL4/…`, `projects/…`, `tools/nanopb`, `tools/opensbi`.

`repo` reproduces exactly that layout from a manifest, which is why it was
chosen over a bespoke fetcher: the alternative is re-implementing the layout
rules above and re-verifying them against every seL4 upgrade.

### Tarball sources

`repo` fetches git projects. A component whose upstream git server is not a
reliable fetch target is vendored as its official release tarball instead,
pinned in `manifests/sources.toml` by sha256 and verified against the project's
own detached signature before it is extracted. `scripts/fetch_sources.py` does
the fetching, verification and extraction, and `make deps` runs it after the
`repo` sync and before the patches (a patch may target a tarball source).

musl is the case that forced this: its official git server serves `git://`
(blocked on some hosts), and its https URL redirects to a cgit web view rather
than a git remote, so `repo` cannot fetch it. The official release tarball is
also the canonical artifact, so the pin is stronger for it — a content hash and
a signature, not a mirror's commit. The signing key is committed at
`manifests/musl-signing-key.asc`; verification dearmors it here and hands the
result to `gpgv`, the standalone verifier, which takes a keyring file directly
and never reads the host's keyring, trust database or keyboxd (`gpg`'s
`--keyring` is silently ignored when a host runs keyboxd, which is why `gpg` is
not used). `gpgv` is therefore the host prerequisite (see `specs/build.md`).

### Sources of truth

| File | Role |
| --- | --- |
| `manifests/aegir.xml` | **The git pins.** Our curated composition. |
| `manifests/sources.toml` | **The tarball pins**, with the release signature and key to verify them. |
| `manifests/musl-signing-key.asc` | The musl release signing key, committed as a trust anchor. |
| `manifests/upstream-16.0.0.xml` | Verbatim upstream release manifest, for audit/diffing. |
| `manifests/aegir-pinned.xml` | Generated by `repo manifest -r`; the frozen record of the git projects a given build used. |

Revisions appear only in the manifests — never duplicated into prose, which
would drift.

### Accepted trade-offs

`repo` is the right tool here, but it is not a perfect fit. These are known,
mitigated, and must stay mitigated:

| Trade-off | Mitigation |
| --- | --- |
| `repo` fetches and may update *itself* at runtime (unpinned third-party code running inside our tree) | `scripts/sync_deps.py` passes a pinned commit to `repo init --repo-rev` from the `[repo_tool]` section of `manifests/toolchain.toml`, instead of the default moving `stable` branch |
| No native patching support | `third_party/patches/<project path>/*.patch`, applied idempotently by `scripts/apply_patches.py`; `make deps-check` fails if a patch is missing or unapplied |
| `repo sync` may reset or discard changes in vendored trees | Vendored trees are **read-only**. We never commit, branch or edit inside them; every change of ours lives in `patches/`. `make deps` never passes `--force-sync`; `make deps-force` exists for recovery and says so |
| Git pins are SHAs, not content hashes | Acceptable: git's object hashing is the upstream trust anchor. `repo manifest -r` + `make deps-check` bind the SHAs we build. Tarball sources are pinned by sha256 and a release signature, which is stronger |
| `.repo/` holds the tool plus a bare copy of every vendored repo | Gitignored, never committed. It is not part of the repository |
| Full clones are large and slow; upstream defaults to a Google-hosted clone bundle | `scripts/sync_deps.py` uses `--no-clone-bundle` and **does not** use `--depth`: our pinned revisions are release-point commits that are not necessarily branch tips, and a shallow fetch would not reliably contain them. Disk is cheap; a silently wrong checkout is not. Deepen/bisect tuning can come later, measured |

## Patches

- Location: `third_party/patches/<project path>/<nnnn>-<slug>.patch`, where the
  directory mirrors the vendored layout (`kernel/`, `projects/musllibc/`, …).
  A patch directory that is not a project path from `manifests/aegir.xml` is
  rejected.
- Format: plain `git apply`-able patches generated with `git format-patch` or
  `git diff` from the pinned revision.
- Applied automatically during `make deps`; `scripts/apply_patches.py` is
  idempotent (it detects an already-applied patch and skips it) and
  `make deps-check` reports any patch that is not applied.
- **Kernel patches are different in kind.** Any change to `kernel/` is
  GPL-2.0-only, must be published, invalidates the seL4 proofs for that
  configuration, and per seL4's trademark policy means the result may no longer
  be called "seL4". A patch to `kernel/` therefore requires a written
  justification in this file before it is added. Prefer patching a
  BSD-2-Clause component, or carrying the workaround in Aegir's own code.

## Licensing obligations

seL4's own licensing model (https://sel4.systems/Legal/license.html) is what
makes an MIT-licensed OS on a GPL-2.0 kernel legitimate: the GPL applies to
kernel code only, the license "stops at the kernel/user code boundary", and the
syscall headers are BSD-2-Clause, so user-level code is not derived work.
Obligations we carry as a result:

1. Aegir's `LICENSE` covers Aegir's code only and says so. We never apply our
   license headers to vendored files (which we do not commit anyway).
2. **Distribution:** an image that embeds `kernel.elf` conveys a GPL-2.0-only
   binary, so a release must accompany it with the corresponding source —
   the exact upstream revision pinned in `manifests/aegir.xml`, unmodified — or
   a written offer to provide it, plus the upstream license texts.
3. The `LICENSES/` directories shipped inside the vendored trees are the
   license texts used for that distribution.
4. seL4's documentation is CC-BY-SA-4.0: do not copy its prose into Aegir's
   specs or docs; link to it instead.
5. If a `kernel/` patch is ever accepted (see above), it is GPL-2.0-only and
   must be published alongside the binaries.

This is engineering policy derived from the upstream licenses, not legal advice.

## Upgrading seL4

1. Pick the upstream release manifest (e.g. `sel4test-manifest` tag `17.0.0`);
   copy it to `manifests/upstream-17.0.0.xml`.
2. Update the revisions in `manifests/aegir.xml`; keep the component set
   identical unless the change is deliberate.
3. `make deps` and `repo manifest -r -o manifests/aegir-pinned.xml`.
4. Re-apply every patch in `third_party/patches/`; fix up or drop each one.
5. Re-run `make build test` (sel4test must be green) and `make deps-check`.
6. Refresh `THIRD-PARTY.md` if a component or its license changed; record the
   move in the commit message.

## Verification

`make deps-check` (`scripts/check_pins.py`) fails if any vendored tree is missing,
sits at a revision other than its pin, is dirty beyond the expected patches, or
has lost its upstream license file. Tarball sources are checked instead by
content hash and signature: a cached tarball that does not match its sha256, a
signature that does not verify against the pinned key, or a tree not extracted
from the pinned tarball all fail the check.
