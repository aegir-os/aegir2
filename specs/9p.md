# 9P: a host directory as a volume

A run is sealed: the initrd is baked at build time and the disk is written once
and read back through a throwaway overlay. Getting a file *into* a running
machine, or a file the machine wrote *out* of it, means rebuilding the image.
9P is the way out: the host shares a directory, the guest mounts it as a
volume, and the ordinary file protocol reaches it. `specs/net.md` moved data
across a wire; this moves it across a device, and it is the one piece of the
machine whose purpose is the development loop rather than the system.

The design is three layers, and the split is the point:

- **the codec** — `libs/freestanding/aegir-9p`'s `aegir/9p.h`. 9P2000.L
  messages written into a buffer and read back: the seven-byte header
  (`size[4] type[1] tag[2]`), the field order, the qid, the open flags. It knows
  nothing about fids, files, or how a message travels.
- **the transport** — `apps/freestanding/aegir-virtio-9p` and the port in
  `aegir/p9transport.h`. A transport carries two buffers, a T-message out and
  an R-message back; it knows nothing about what the messages mean.
- **the filesystem** — `apps/freestanding/aegir-fs-9p`, a service that speaks
  the volume protocol (`aegir/volume.h`) and turns each call into 9P messages.
  It knows nothing about virtio.

"Any 9P filesystem" is what the first two layers buy: a TCP transport or a
shared-ring one would be a new transport serving the same port, and the
filesystem would not know.

## Why not one service

The device manager owns devices and launches their drivers, but it hands a
driver only `log.main`, its port and its interrupt — deliberately not
`vfs.namespace`, because a device manager that knows about the VFS is not a
device manager. And director cannot grant the device: every virtio transport
answers the same `compatible` (`virtio,mmio`), so the register window is what
says *which* device, and only the device manager probes it. So the frame can
reach a devmgr-spawned driver and a volume can only be registered by a
director-spawned service — two processes, exactly the split `specs/net.md`
already uses: a driver a service opens through the registry, and a consumer
that opens it.

## The wire

virtio-9p is device id 9, one request virtqueue, and one feature bit
(`VIRTIO_9P_MOUNT_TAG`). Its config space is the export's name: a 16-bit
length then the bytes. It is not in the OASIS spec — the spec's "File System
Device" is virtio-fs (FUSE, id 26) — so the shapes here come from QEMU's
`hw/9pfs/virtio-9p-device.c` and Linux's `net/9p/trans_virtio.c`:

- One request is a **two-descriptor chain**: a device-readable buffer holding
  the T-message, then a device-writable buffer the R-message lands in. QEMU
  reads the seven-byte header off the first and pushes the chain back with the
  reply's length; a buffer cannot be both read and written by the device, which
  is why the caller supplies both halves rather than one.
- The dialect is **9P2000.L**, little-endian: `stat`/`wstat` are
  `getattr`/`setattr`, and `readdir`, `mkdir`, `unlinkat` and `renameat` exist.
  A reply is its request's type plus one, and `NOTAG` (0xffff) is the version
  handshake's tag.

## The transport port

The driver serves one method through a shared window split in half
(`aegir/p9transport.h`):

- `info` — no words; the answer is the mount tag as the namespace's string
  shape. It is the export's name, and the volume is named after it.
- `round-trip` — the request's length in bytes. The caller has written the
  request into the window's first half; the driver points the device's two
  descriptors at the halves' *physical* addresses, so neither side copies, and
  answers the reply's length. The caller reads the reply from the second half.

Both sides compute the split from the window's size — the driver from its
grant, the client from the registry's geometry — so a larger window is a larger
message without a second number to agree on. The window row is `window=17`
(128 KiB), so each half carries a 64 KiB message.

## The machine has eight virtio slots

QEMU's RISC-V `virt` machine creates exactly eight `virtio-mmio` transports
(`VIRTIO_COUNT` in QEMU's `include/hw/riscv/virt.h` — a compile-time constant,
not a machine option), and all eight were in use: rng, block, keyboard,
tablet, mouse, two displays, and net. The ninth device for 9P did not fit
(`A 'virtio-bus' bus was found but is full`). A slot had to be freed, and the
second display was the one given up: the machine now has one head
(`gpu.virtio0`), and the driver-protocol mode test that poked the parked head
went with it. Every other acceptance stands.

## What a run gets

`scripts/targets.py` adds `-fsdev local,id=fsdev0,path=host,security_model=none`
and `-device virtio-9p-device,fsdev=fsdev0,mount_tag=host`. QEMU resolves
`path=host` under its working directory, the build directory, where the runner
creates it (`scripts/run_target.py`'s `ensure_host`) and drops one known file.
`AEGIR_9P_DIR` makes the share a symlink to a real host tree instead, for
interactive work — the machine's own directory, read and written.

## Phases

1. **The transport, proved.** The driver does the handshake, reads the tag,
   lays out the queue, and answers a `Tversion`/`Rversion` round trip before it
   says `ready` — queue, kick, completion and reply, with no filesystem built
   on it. Cue: `p9.virtio0: 9P2000.L, msize N, tag host`. **Landed.**
2. **A read-only volume.** `aegir-fs-9p` opens `p9.virtio0` through the
   registry, runs the 9P client (`version`, `attach`, `walk`, `lopen`,
   `Tread`, `getattr`, `readdir`, `statfs`) and serves `read`, `list`, `stat`
   and `space`, registering the export's tag as a volume. Acceptance: listing
   and reading a file the runner put in the host directory.
3. **The write side.** `lcreate`, `Twrite`, `mkdir`, `unlinkat`, `renameat`,
   `setattr` (truncate) and the handle table, serving `open`, `write`,
   `mkdir`, `remove`, `rename` and `truncate`. Acceptance: the machine writes
   a file the runner finds in the host directory afterwards.

## Not this

A 9P *server* (Aegir exporting a volume to the host); the DAX window and
zero-copy transfers (Linux's `p9_virtio_zc_request`); symlinks, mknod, xattrs
and locks; more than one export at a time. Each is a later slice, and none of
them moves the seam: the codec and the transport port are the interfaces the
rest would build on.
